# Fighter-jet flight model and controls for UE5 C++ (arcade to semi-realistic)

Scope: how to build a CPU-cheap fighter flight model on a rigid body in UE5 (5.4–5.9), which open references to copy from, how to keep it stable at 100–600 m/s, and how to map keyboard, mouse and gamepad. Context: the Boat Race project already runs a custom force model on a `UPrimitiveComponent` rigid body (`BoatPawn`: buoyancy probes, hydrodynamics, engine, rudder) with tuning as `UPROPERTY(Config)` and a Python mirror (`physics_check.py`). A jet model of the same shape fits that pattern directly.

Note on sources: web search found few authoritative numbers for real fighter performance; real-aircraft figures below are flagged where they come from blogs or simulator forums. Several engine-behaviour claims come from Unreal forum threads, not Epic documentation. I could not find the local UE 5.9 engine source on this machine to confirm API signatures (a filesystem search for `Engine/Binaries/Linux/UnrealEditor` found nothing at depth 6), so the C++ names below should be checked against the engine headers before use.

## 1. Flight model options and the equations behind them

### Takeaway
For a four-player combat game on integrated graphics, the proven pattern is the "semi-arcade" model popularised by Vazgriz: a rigid body with thrust, a v²-scaled drag, a lift force from a hand-drawn CL(AoA) curve, an induced-drag term proportional to CL², and **steering done by driving angular velocity directly toward a target rate** (not by simulating control surfaces), with a G limiter that scales the input. It costs a handful of vector maths per step, is stable, and gives real energy bleed and a corner speed for free. Full 6-DOF aero (JSBSim) is available as an Epic-originated UE plugin but is simulator-grade, LGPL and overkill.

### Cited Findings

**The three tiers**
- Pure arcade (kinematic: rotate by rate × input, velocity follows the nose) has no open primary write-up found; it is the "Standard" mode feel in Ace Combat 8 that "automatically turns the aircraft in the direction you push" — [GamerBlurb](https://gamerblurb.com/guides/ace-combat-8-standard-vs-expert-controls) (fan guide, not Bandai Namco).
- Semi-arcade: Vazgriz's design principle is to "fake as much as possible" rather than simulate airflow; forces come from simple formulas with hand-tuned coefficients — [Vazgriz, Flight Sim Part 1](https://vazgriz.com/346/flight-simulator-in-unity3d-part-1/).
- Full FDM: JSBSim ships an Unreal Engine plugin/reference application, "initially created by the Simulation Team at Epic Games as a demonstration of UE5 for serious flight simulation", MIT for the UE app, LGPL-2.1 for the JSBSim core — [JSBSim README](https://raw.githubusercontent.com/JSBSim-Team/jsbsim/master/README.md); [search summary of JSBSim UE plugin](https://forums.unrealengine.com/t/combat-flight-simulator-prototype-in-unreal-5-jsbsim/569418).
- JSBSim in UE has reported high-speed oscillations; a newer plugin version runs the FDM at a constant 120 Hz, and capping frame rate (`t.MaxFPS`) helped — [UE forum: Combat Flight Simulator Prototype + JSBSim](https://forums.unrealengine.com/t/combat-flight-simulator-prototype-in-unreal-5-jsbsim/569418). One user reported that setting `Commands` on `JSBSimMovementComponent` did not reach the flight model (single report) — same thread.
- A 2025 paper describes integrating JSBSim (dynamics) with UE (visuals) for a Cessna T-37 — [ASAT journal](https://asat.journals.ekb.eg/article_453595.html).
- Chaos Vehicles can fly in a limited way: `UChaosVehicleMovementComponent` has an optional `Aerofoils` array (`FVehicleAerofoilConfig`: type Fixed/Wing/Rudder/Elevator, area, stall angle, up axis, bone + offset; "larger value creates more lift but also more drag") and `ApplyAerofoilForces` / `ApplyThrustForces` — [UE API: UChaosVehicleMovementComponent](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/ChaosVehicles/UChaosVehicleMovementComponent); [FVehicleAerofoilConfig](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/ChaosVehicles/FVehicleAerofoilConfig). Chaos Modular Vehicle has `UVehicleSimAerofoilComponent` — [UE API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/ChaosModularVehicleEngine/UVehicleSimAerofoilComponent). No tutorial for a thrust-driven aircraft built on these was found.

**Vazgriz semi-arcade model, step by step** — all from [Vazgriz Part 1](https://vazgriz.com/346/flight-simulator-in-unity3d-part-1/):
- State each step: local velocity v_l = R⁻¹·v, local angular velocity likewise. **Pitch AoA = atan2(−v_y, v_z)**, **yaw AoA (sideslip) = atan2(v_x, v_z)** (Unity: z forward, y up). Measured G = Δv_world/dt rotated into local space.
- **Thrust** = throttle (0–1) × maxThrust along forward axis.
- **Drag** D = ½ρv²ACd simplified to Cd·v², opposing velocity. Cd is direction-dependent: six curves (forward/back, left/right, up/down) evaluated on |local velocity component|, blended (`Scale6`). "A Cd of 1 works fine." Airbrake and flaps add to the forward Cd only. A low-speed curve reduces drag further.
- **Lift** L = ½ρAC_L v² simplified to v²·C_L(AoA)·liftPower. Direction: project velocity onto the plane perpendicular to the wing's lateral axis; lift = cross(projected velocity dir, lateral axis). **C_L curve over −90°…+90°: 0 at 0°, peak 1.0 at 30°, falls beyond 30° (stall), odd-symmetric for negative AoA.** liftPower = 150 (unitless, tuned).
- **Induced drag** (physics: C_Di = C_L²/(πARe)) kept only as C_L² dependence: magnitude = v²·C_L²·inducedDrag·inducedDragCurve(max(0, forwardSpeed)), opposite projected velocity.
- **Flaps**: add flapsLiftPower to liftPower, add flapsAOABias to AoA, add flapsDrag.
- **Vertical stabiliser**: same lift function on yaw AoA about the vertical axis with rudderPower — stabilising force only, no torque.
- **Steering**: target angular velocity = input × turnSpeed × steeringPower, with steeringPower = steeringCurve(forwardSpeed) (less authority when slow). Per axis, error = target − current ω, change clamped to turnAcceleration × steeringPower × dt, applied as a **velocity change (mass-independent)**. Control surfaces are not simulated; the plane stops rotating when input is released.
- **G limiter**: predicted acceleration from a given input ≈ cross(V, ω_target). Limit chosen by input direction (gLimit for most, gLimitPitch for pull-up), × 9.81. Scale input to unit magnitude; if predicted G > limit return limit/predictedG else 1. Scaling avoids a dead band where 50–100% stick gives no extra turn. Example values: 8 G typical, aircraft structurally capable of ~16 G at high speed; human negative-G limit ~−4 G.
- **Corner speed emerges**: below it, turn rate is limited by control authority (steeringCurve); above it, by the G limiter. Energy is tuned with maxThrust, inducedDrag and inducedDragCurve.
- Values not published in the article: maxThrust, inducedDrag, turnSpeed, turnAcceleration, steeringCurve shapes, final gLimit (they live in the project's GitHub repo, tags `part-1`/`part-2`/`part-3`) — [Vazgriz itch.io Part 2](https://vazgriz.itch.io/flight-sim-part-2), [Part 3](https://vazgriz.itch.io/flight-sim-part-3).

**Aerodynamics reference**
- Induced drag C_Di = C_L²/(π·AR·e); AR = span²/area; e = 1.0 for an elliptical lift distribution, less otherwise, e = 0.7 for a rectangular wing — [NASA Glenn, Induced Drag Coefficient](https://www1.grc.nasa.gov/beginners-guide-to-aeronautics/induced-drag-coefficient/).
- Corner speed is the crossover between lift-limited and G-limited turning and is where maximum instantaneous turn rate occurs; max C_L and max load factor occur simultaneously there — [Virginia Tech AOE 3104 turning flight notes](https://archive.aoe.vt.edu/lutze/AOE3104/turningflight.pdf) (via search summary).

**Fighter performance numbers (weakly sourced)**
- F-16 instantaneous turn rate ~25.5°/s at low altitude between 300–450 kt; sustained ~14°/s at Mach 0.8, 15,000 ft — [BoltFlight blog](https://boltflight.com/f-16-turn-rate-a-detailed-analysis-of-maneuverability/) (no test data cited). Sustained "around 15°/s where Ps = 0" — [War Thunder forum](https://forum.warthunder.com/t/f-16-fighting-falcon-history-performance-discussion/916?page=4).
- A DCS test: full 360° at ~1,000 ft bleeding 400→250 kt took 17.25 s (≈21°/s average) — [DCS forum](https://forum.dcs.world/topic/280462-dcs-f16-turn-performance/page/5) (simulator result).
- Missiles in Vazgriz's AI part turn at max (turningG × 9.81)/speed rad/s, example 8 G — [Vazgriz Part 3](https://vazgriz.com/503/creating-a-flight-simulator-in-unity3d-part-3/).

### Inferences
- **Core turn kinematics (standard physics, my derivation):** turn rate ω = g·√(n²−1)/V; radius r = V²/(g·√(n²−1)). At n = 9: V = 150 m/s (540 km/h) → ω ≈ 33.5°/s, r ≈ 256 m; V = 200 m/s (720 km/h) → ω ≈ 25°/s, r ≈ 455 m; V = 300 m/s (1080 km/h) → ω ≈ 17°/s, r ≈ 1.0 km; V = 550 m/s (~2000 km/h) → ω ≈ 9°/s, r ≈ 3.4 km. These line up with the weakly sourced 21–25°/s F-16 figures, so they are a sound sanity check for tuning.
- **Corner speed** V_c = √(2·n_max·m·g / (ρ·S·C_Lmax)). With assumed F-16-like values (m = 12,000 kg, S = 27.9 m², C_Lmax ≈ 1.6, ρ = 1.225, n = 9) V_c ≈ 197 m/s ≈ 710 km/h ≈ 380 kt. Assumed inputs, not sourced; use as an order of magnitude.
- **Suggested game ranges** (design judgement, not sourced): stall/min control 180–250 km/h; cruise 700–900 km/h; top speed with afterburner 1,500–2,000 km/h; G limit 7.5–9 (player), 20–40 G for missiles; instantaneous turn 25–35°/s at corner; sustained 12–18°/s; roll rate 180–270°/s (arcade fighters commonly feel right around 200°/s); yaw rate 10–20°/s. Compress real numbers: an arena of a few km is crossed in seconds at Mach 1, so many arcade games cap speeds near 1,200–1,500 km/h and scale the map.
- C_L(α) slope for a finite wing is roughly 0.07–0.1 per degree (thin-airfoil 2π/rad reduced by AR); Vazgriz's curve (1.0 at 30°) is deliberately flatter and later-stalling than reality — fighters stall around 20–35° with strakes, so 25–30° peak is a defensible choice.
- **Energy bleed** in a turn comes entirely from induced drag ∝ C_L²v² = (n·W)²/(½ρv²S)²·v² ∝ n²/v². So bleed grows with the square of G and falls with speed — exactly the "dump speed in a hard turn" feel. Tune inducedDrag so that a 9 G turn at corner speed with full afterburner loses ~20–40 km/h per second.
- Use **SI internally** (m, kg, m/s) and convert to UE centimetres only at `AddForce`/`SetPhysicsLinearVelocity`, as the boat code presumably already does; or apply accelerations via `AddForce(..., bAccelChange=true)` / `AddTorqueInRadians(..., bAccelChange=true)` to make mass irrelevant like Vazgriz's velocity-change steering.
- For this project a **semi-arcade force model on the existing rigid-body pattern** is the right tier: it reuses the `BoatPawn` architecture, can be mirrored in a Python check like `physics_check.py` (stall speed, top speed, corner speed, sustained turn, frame-rate independence), and costs microseconds per jet. Chaos Vehicles aerofoils add a plugin dependency (the project avoids extra plugins) for little gain; JSBSim adds an LGPL library and per-aircraft XML.

## 2. UE5 implementation: rigid body forces vs Chaos vs kinematic, fixed stepping, and tunnelling

### Takeaway
Run the force model at a fixed rate. In UE5 the supported route is **Project Settings → Physics → Tick Physics Async** with an **Async Fixed Time Step Size** (e.g. 1/60–1/120 s) and per-actor/component async physics tick; classic substepping is reported to be effectively non-functional under Chaos and mutually exclusive with async. Alternatively (simpler, and probably what the boat already does), compute forces in normal Tick and verify frame-rate independence with a Python mirror. For collisions at 300+ m/s, use **CCD on the jet body** plus a **manual sweep/line trace from last to current position** for ground/sea impact and for bullets.

### Cited Findings
- Substepping settings: Substepping, Substepping Async, Max Substep Delta Time (e.g. 0.05 s frame with 0.025 max → 2 substeps), Max Substeps, Max Physics Delta Time; smaller max substep is more stable but costs more CPU; forces applied for a frame are applied across all its substeps; collision callbacks are deferred to the last substep and can arrive multiple per frame — [Epic: Physics Sub-Stepping](https://dev.epicgames.com/documentation/unreal-engine/physics-sub-stepping-in-unreal-engine?lang=en-US). The page does not mention Chaos or `FCalculateCustomPhysics`.
- Community reports: substepping and async physics are mutually exclusive and "Substepping Async" is effectively unused; Chaos has "no actual sub-stepping" and the substep function is empty; recommended approach is enable Tick Physics Async and set the fixed timestep with substepping off — [UE forum: Tick Physics Async and Substepping](https://forums.unrealengine.com/t/relationship-between-tick-physics-async-and-substepping/2395435); [UE forum: How does physics substepping in UE5 work?](https://forums.unrealengine.com/t/how-does-physics-substepping-in-ue5-work/654384/2); [UE forum: Sub-stepping in C++ in UE5 and Chaos](https://forums.unrealengine.com/t/how-to-do-sub-stepping-in-c-in-ue5-and-chaos/578622/4).
- Async tick hooks: enabling the setting allows optional `AsyncPhysicsTick()` on actors and `AsyncPhysicsTickComponent()` on components; one thread reports the callback still runs on the game thread once per physics step while the game thread no longer waits — [UE forum: Exposing UE5 TickPhysicsAsync](https://forums.unrealengine.com/t/exposing-ue5-tickphysicsasync-event/271744); [Is Async Physics Tick really async?](https://forums.unrealengine.com/t/is-async-physics-tick-really-async/2353151).
- Pitfalls: if frame rate falls below the async rate with Max Physics Delta Time limiting, the game slows down; with Max Physics Delta Time 0.0333 and step 0.01, async ticks 100×/s while fps > 30 — [UE forum: physics tick independent of fps](https://forums.unrealengine.com/t/how-to-get-absolute-physics-tick-rate-calculations-independent-of-fps/1224018). `AddForce` in async tick appeared to scale with game-frame time in one report — [UE forum: Add force works strange in async tick](https://forums.unrealengine.com/t/add-force-works-strange-in-async-tick-physics/1924807). `SetWorldLocation` from async tick crashed; an assertion in `PhysScene_Chaos.cpp` and a community async plugin crashing after ~1 min were reported — [UE forum: How to access async physics](https://forums.unrealengine.com/t/how-to-access-async-physics-in-ue5/505696); [Async Physics Crashes](https://forums.unrealengine.com/t/async-physics-crashes/2601520). Chaos Vehicles' own approach (a sim callback object on the physics thread) was copied by a community plugin — [UE forum thread](https://forums.unrealengine.com/t/exposing-ue5-tickphysicsasync-event/271744/7); an article on async suspensions in UE5 — [Taming Chaos (gitconnected)](https://levelup.gitconnected.com/taming-chaos-stable-vehicle-suspensions-with-async-physics-in-ue5-566369c7b097).
- CCD: per-body `bUseCCD` (`BodyInstance.bUseCCD = true`, runtime `SetUseCCD`); also make sure both actors block the relevant channels; ProjectileMovementComponent does not use physics, so CCD/substepping do not apply to it — sweep instead; a developer stores previous and current positions and line-traces between them — [UE forum: Projectiles going through objects even with CCD](https://forums.unrealengine.com/t/projectiles-going-through-objects-without-overlapping-even-with-continuous-collision-detection-on/148653); [High velocity collision detection](https://forums.unrealengine.com/t/high-velocity-collision-detection-best-practice/298725). Chaos CCD "will take any opportunity to bail out" below a movement threshold and can still tunnel; CCD helps detection not solving — [UE forum: Chaos contact modification with CCD](https://forums.unrealengine.com/t/chaos-contact-modification-behaves-oddly-with-ccd/2689496).

### Inferences
- **Recommended C++ structure** (mirrors `BoatPawn`): `AJetPawn` with a `UStaticMeshComponent`/box root simulating physics, gravity on, linear/angular damping ≈ 0 (drag is ours), mass ~12,000 kg (or any mass if using accel-change). Each step: (1) read v, ω in local frame; (2) compute AoA, sideslip, dynamic pressure; (3) thrust, drag (incl. airbrake), lift, induced drag, side force → `AddForce`; (4) steering: target ω from input × rate × steeringCurve(speed) × GLimiter → clamp Δω by turnAccel·dt → `SetPhysicsAngularVelocityInRadians` or `AddTorqueInRadians(..., bAccelChange=true)`; (5) assists (auto-level, stall/ground protection).
- **Fixed step without async**: an in-pawn accumulator (run N fixed 1/120 s sub-steps of the force maths inside Tick, summing to one `AddForce` per frame) does not work because the solver integrates once per frame; only async tick or a pure kinematic integrator gives real fixed steps. The pragmatic option is per-frame forces plus explicit dt use and a Python check at 20–120 fps, which the boat already proves works.
- **Kinematic option for maximum stability and cheapest networking**: integrate the whole flight model yourself (semi-implicit Euler at fixed 1/120 s with an accumulator, interpolate the render transform) and move the actor with `SetActorLocationAndRotation(..., bSweep=true)`. The sweep gives tunnelling-free collision for free, the physics engine never sees a 300 m/s body, and it matches the project's "owner simulates, others hold a kinematic copy" rule. Cost: a sweep per jet per step (cheap with a capsule/box).
- At 300 m/s and 60 fps a jet moves 5 m per frame; at 600 m/s, 10 m. Terrain is large so CCD on the body is usually enough; thin objects (gantries, bridges, cables) need sweeps. Bullets (~1,000 m/s, 17 m/frame) should be hitscan or segment traces, never physics bodies — the project's deck gun already decides hits with traces.
- Sea-level crashes should use the one wave function (`OceanWaves`) rather than collision, per the project's design rule.

### Gaps
- Exact UE 5.9 signatures of `AsyncPhysicsTickActor`/`AsyncPhysicsTickComponent`, the `bAsyncPhysicsTickEnabled` flag and `UPhysicsSettings::AsyncFixedTimeStepSize` could not be verified (engine source not found locally; no official doc page found).
- Whether Chaos honours `bUseCCD` well for a large fast body against landscape/procedural mesh in 5.9 was not confirmed.

## 3. Control schemes: mouse aim, keyboard, gamepad, assists and PID

### Takeaway
Offer three schemes behind one "desired rates" interface: **(a) mouse aim** (War Thunder "instructor"/MouseFlight style: mouse moves a world-space aim direction relative to the camera; an autopilot computes pitch/roll/yaw to bring the nose onto it), **(b) gamepad "Standard"** (left stick X turns: auto-bank + pull, Ace Combat style) and **"Expert"** (left stick X rolls, Y pitches, shoulders yaw), **(c) keyboard direct** (W/S pitch, A/D roll, Q/E yaw). All schemes output normalised commands that the flight model converts to target angular rates, then the G limiter scales them.

### Cited Findings
- **War Thunder mouse aim**: an AI "Instructor" converts the mouse position into control commands; the mouse never moves control surfaces directly but keys still do; the instructor can only be fully disabled in full-real or relative controls; players note poor turn coordination in mouse aim — [War Thunder: How the instructor works (news)](https://warthunder.com/en/news/4366-wiki-article-how-the-instructor-works-en); [War Thunder forum: coordination on mouse aim](https://forum.warthunder.com/t/can-we-talk-about-aircraft-coordination-in-wt-on-mouse-aim/69953). A vendor blog calls the instructor a PID controller with the mouse as setpoint — [AttackShark blog](https://attackshark.jp/blogs/knowledges/war-thunder-mouse-aim-sensor-calibration-guide) (unofficial).
- **MouseFlight (open-source, Unity)**: mouse rotates an empty "Mouse Aim" transform *relative to the camera* so screen-left is always left; aim point = MouseAim.forward × AimDistance; an orbit camera rig follows the aim separately for smoothness, kept level to world up except near vertical; the plane flies toward the crosshair via steering behaviours; W/S pitch and A/D roll override; C free-look — [brihernandez/MouseFlight](https://github.com/brihernandez/MouseFlight). (Steering constants are in the repo's scripts, not the README.) A UE forum thread discusses the same in UE — [UE forum: War Thunder style mouse aiming](https://forums.unrealengine.com/t/war-thunder-style-mouse-aiming-flight-control/1683477/5).
- **Ace Combat 7**: Standard — left stick X turns the aircraft; Expert — left stick X rolls; yaw on L1/R1 in both; set in Options → Flight System — [GamePressure](https://gamepressure.com/ace-combat-7/standard-and-expert-handling-modes/zabcd1); [Shacknews AC7 controls](https://shacknews.com/article/109486/ace-combat-7-controls-playstation-4-and-xbox-one). Ace Combat 8: Standard helps keep the aircraft level; control mode is independent of difficulty — [GamerBlurb](https://gamerblurb.com/guides/ace-combat-8-standard-vs-expert-controls).
- **Vazgriz gamepad layout**: left stick roll and pitch, gamepad required; airbrake with gear down is wheel brake — [itch.io Part 2](https://vazgriz.itch.io/flight-sim-part-2).
- **Vazgriz AI steering (usable for mouse-aim autopilot too)**: target into local space; pitch error from `SignedAngle` in the YZ plane; if target is >15° (`pitchUpThreshold`) below, pitch up instead (roll over and pull rather than push negative G); if within `fineSteeringAngle` of the nose, use yaw for fine aim, otherwise roll toward the target scaled by `rollFactor` (~0.01); clamp to ±1 and smooth with MoveTowards(steeringSpeed·dt); ground avoidance raycast 10° below the nose → level wings and full pull; low-energy state levels and flies straight — [Vazgriz Part 3](https://vazgriz.com/503/creating-a-flight-simulator-in-unity3d-part-3/). He uses no PID.

### Inferences
- **Mouse-aim autopilot (recommended algorithm)**, combining MouseFlight + Vazgriz: 
  1. Aim direction A (world) is rotated by mouse delta × sensitivity in camera space; clamp its angle from the nose (e.g. ≤ 90–120°) so it cannot be lost behind.
  2. Local target t = R⁻¹·A. Pitch error θ = atan2(t_up, t_fwd); yaw error ψ = atan2(t_right, t_fwd).
  3. Desired bank: if the angle off nose > ~5–10° ("aggressive turn" zone) roll so the target sits in the lift plane: roll error φ = atan2(t_right, t_up) (bank to put target overhead); else roll toward wings-level (φ = current bank vs world up) and use yaw for fine tracking.
  4. Commands: pitch = clamp(Kp_p·θ − Kd_p·ω_pitch), roll = clamp(Kp_r·φ − Kd_r·ω_roll), yaw = clamp(Kp_y·ψ − Kd_y·ω_yaw). Blend roll between "bank to target" and "level" by angle off nose (smoothstep 5°→15°).
  5. Feed to the same rate/G-limited steering as manual input. Because the flight model already tracks a target angular rate, a **PD on angle (P on error, D using measured ω)** is usually enough; integral is rarely needed and causes overshoot; if added, clamp it (anti-windup) and reset on large errors.
  - Starting gains (normalised commands, errors in radians): pitch Kp ≈ 3–6, roll Kp ≈ 2–5, yaw Kp ≈ 2–4, Kd ≈ 0.1–0.4× Kp seconds. Tune by step response: raise Kp until a 30° pitch step overshoots slightly, then add Kd until overshoot <5%. Classic Ziegler–Nichols (Kp = 0.6 Ku, Ti = Pu/2, Td = Pu/8) is a starting point if you find the ultimate gain Ku and period Pu. (General control theory, not sourced in this research.)
- **Gamepad "Standard" (assisted)**: stick X → desired heading rate; controller computes bank angle φ_cmd = atan(V·ψ̇/g) (coordinated-turn relation), rolls to it, and pulls the G needed n = 1/cos φ plus stick Y. Releasing the stick rolls wings-level (auto-level at ~60–90°/s). Stick Y → pitch rate; L1/R1 yaw; triggers throttle (RT accelerate/afterburner past a detent, LT brake/airbrake); right stick camera look; face buttons gun/missile/flare/target cycle.
- **Gamepad "Expert"**: stick X → roll rate, Y → pitch rate, shoulders yaw, no auto-level. Apply an input curve (e.g. out = sign·|x|^1.5–2 or a blended cubic) and a 5–10% deadzone, as the boat steering presumably already does.
- **Keyboard direct**: W/S pitch (offer invert, default pull = S or "W nose down" airline convention — make it a setting), A/D roll, Q/E yaw, Shift/Ctrl throttle up/down with held-key ramp (~0.5–1.0/s) or Shift = afterburner, Space airbrake. Keyboard is digital, so ramp inputs (rise ~4–8/s, fall faster) to avoid jerky full-rate snaps; combine with the G limiter so a held key cannot overstress.
- **Assists that convert stick to G/roll rate**: map stick pitch to *commanded G* (n_cmd = 1 + y·(n_max−1) for pull, down to −3 for push) rather than rate at high speed; at low speed the steeringCurve limits rate. Roll stick → commanded roll rate (max 180–270°/s, falling at low speed). Add AoA limiter (cap pitch command when AoA > ~25° unless "post-stall" mode) and a stall-recovery assist (nose down when speed < stall + margin). Ground-collision avoidance: raycast/time-to-impact along velocity; if < ~3–5 s, override with level-and-pull (Vazgriz approach).
- **Throttle model**: throttle 0–1 with afterburner region above ~0.85–0.9 (or a separate button) giving 1.4–1.6× thrust and higher fuel/heat; airbrake adds forward Cd ~0.5–1.5. Thrust-to-weight for modern fighters is ~1.0–1.2 with afterburner (common knowledge, not sourced here).
- Map everything through UE5 **Enhanced Input** (Input Actions + Mapping Contexts) so each scheme is a mapping context; the project's current controller builds menus in code, and Enhanced Input mapping contexts can also be created in C++ without assets.

## 4. Takeoff and landing: needed or skip?

### Takeaway
Skip them for a combat-first game: start in the air (or catapult "launch" as a scripted burst from a carrier/runway) and treat ground/water contact as a crash. Landing requires gear, wheel friction, flare handling and low-speed aero that a semi-arcade model handles poorly, and it adds nothing to a four-player race/dogfight.

### Cited Findings
- Vazgriz's project does include landing gear, flaps, and wheel brakes (airbrake with gear down = wheel brake), i.e. low-speed handling needs flaps (extra lift, AoA bias, drag) — [Vazgriz Part 1](https://vazgriz.com/346/flight-simulator-in-unity3d-part-1/); [itch.io Part 2](https://vazgriz.itch.io/flight-sim-part-2).
- Commercial UE jet assets advertise takeoff & landing as a feature in their own right, implying non-trivial extra work — [UE forum: Fighter Jet Flight Physics – Takeoff & Landing](https://forums.unrealengine.com/t/ritzredemption-fighter-jet-flight-physics-playable-jet-with-takeoff-landing/2838478).
- Ace Combat 7 treats takeoff/landing as occasional optional/scripted segments rather than core play (general knowledge of the series, not verified in fetched sources).

### Inferences
- **Air start**: spawn at a grid in formation at ~600–800 km/h, throttle at cruise, controls live after the countdown; this matches the boat game's grid/countdown in `BoatRaceGameMode`.
- **Carrier/runway launch as cosmetic**: hold the jet kinematically on a track, accelerate to 300 km/h over ~2 s, then hand over to physics — no wheel simulation needed.
- **Respawn**: wreck recovery already exists for boats; reuse for jets with an air respawn behind the pack.
- If landing is ever wanted, the minimum is: gear as three short sweeps/springs, flaps, a low-speed C_L boost, and an auto-flare assist.

### Gaps
- No primary source on how arcade combat games implement catapult launches; recommendations above are design inference.
